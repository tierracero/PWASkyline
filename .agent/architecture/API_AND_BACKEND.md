# API and Backend Boundaries

Authoritative rules: `API-*`.

## Verified Facts

- Asset-item/trip media retry is client draft behavior through existing uploadManager/asyncCheckUploadStatus endpoints. A fresh raw retry has a new upload event and retains its original destination/type; acknowledged processing resumes without another POST, and stale generations plus event/destination checks protect attachment publication. CreateAssetItem/changeTripStatus/delivery writes are never retried by these controls. No backend/wire/persistence or dependency changes are required.

- getAsset inventory rows now consume optional AssetsItemPayload.serviceTrip/serviceOrder links. SkylineServer forwards the existing saved unit UUIDs; unavailable/transit are not substituted for reservation identity. Existing initializer calls/old JSON remain compatible through nil defaults, but accurate reservation categories require the updated shared TCFireSignal contract and server projection to be released with the clients. No endpoint, request, schema or state-transition change is introduced.

- `CustAcctCharges` and `CustAcctChargesQuick` use the shared `billingType` stored field and initializer label. TCFireSignal responses and PWA account, sale and fiscal views consume those shared values directly; no local charge DTO duplicates the field. Deploy matching shared models, server and clients together after the existing-tenant `CustAcctCharges.type` to `billingType` column rollout. Separate SOC charge projections retain their `type: BillingType` response key through server query aliases. App target compilation verified against the synchronized shared packages; browser/database execution remains unverified.

- Shared summary charge records distinguish `type: ChargeType` from `billingType: BillingType`; the SOC projection exposes its billing classification as `type: BillingType`. Locally appended service/manual charges retain raw source prices and use the adjustment code type or explicit ChargeObject.billingType to retain their billing direction; charge editing retains the source billingType, and approved-budget conversion reads SOC.type using the established adjustment-versus-charge mapping. TCFundamentals owns the models. `CustOrderCreateCharges` and `CustOrderLoadFolioCharges` expose `public var billingType` and matching initializer labels; both decode the earlier chargeType key and encode billingType. `ChargeObject` also encodes/decodes billingType separately from its type identity. SOC decoding accepts the earlier chargeType key and defaults a missing classification to charge. App target compilation was verified for shared-field synchronization; the later App signed-balance changes are source-audited only, with build/browser behavior unverified.

- Trip creation forwards all selected route stops through the existing shared `CreateTripRequest.locations: [TripLocation]`, ordered origin, first destination, then additional destinations. The existing server `makeLocationItems` enumerates request order into persisted snapshot positions. Each merchandise request retains its chosen destination reference; the client checks unique nonempty stop references and reuses linked-asset route validation before submission. No endpoint, wrapper, wire-key, shared-model or server change was needed. Source-audited; build/browser/server execution remains unverified.

- `deliverAssetItem` uses the authenticated trip POST route and shared TCFireSignal `DeliverAssetItemRequest`/`DeliverAssetItemResponse`. The request takes the concrete linked asset item UUID (`FiscalMercanciaItem.merchandiseId`), optional comment, original staged image filenames and optional destination section/subsection IDs (nil defaults). The response identifies the trip, linked asset and merchandise snapshot separately and supplies `deliverd`, trip status, remaining counters and auto-completion. The UI updates from a successful matching response then reloads authoritative trip/notes; no local DTO or wire-key correction replaces the shared spelling. This flow requires TCFireSignal with the delivery contract and TCFundamentals with backward-compatible `deliverd` decoding. Shared packages remain the sole payload/model authority.
- Asset-item editing reuses the existing authenticated `updateAssettem` POST wrapper and TCFireSignal `UpdateAssettemRequest` without contract changes. The client explicitly forwards section/subsection IDs (including intentional nils), current cost in exact Int64 cents, optional serial and name. It refreshes through `getAssetItem(.id)` after success. Existing `listStoreArchitecture` customer reads and `loadStore`/`getAssetsSection` store/warehouse reads supply owner-filtered classification choices. The companion SkylineServer fix now executes the item update and audit note inside one transaction; that backend change must be deployed for persistence.
- The trip `getTrip` client wrapper accepts TCFundamentals `HybridIdentifier` and forwards it as the shared `GetTripRequest.tripId` on the existing authenticated POST route. `.id(UUID)` and `.folio(String)` are supported by the contract; the shared `GetTripItem`/`GetTripResponse` payload and decoding remain unchanged. Existing list/followup opens and post-status refreshes use `.id`.
- The trip `changeTripStatus` client wrapper sends the shared `ChangeTripStatusRequest(tripId:status:comment:media:)` to the existing authenticated POST route and decodes `APIResponse`. Media uses the shared `ChangeTripStatusMedia` records with merchandise item IDs and original filenames; no local DTO or backend wire key is introduced. Evidence uploads and staged previews use unregistered `.assetItem`/`iCatch`; the server copies accepted evidence once to tenant `fileNet` and links the same saved filename to the trip/merchandise and, for assets, Kardex metadata. Source and isolated type checks match the current local TCFireSignal contract; the fetched pinned contract now matches that source.
- Client API wrappers live under `Sources/App/API/**`.
- The client `sincCustSettings` wrapper decodes an immutable reference-backed `SincCustSettingsSnapshot` with the same fields/keys/optionality as the shared `CustComponents.SincCustSettingsResponse`. This avoids passing/copying the whole settings aggregate by value through optional response callbacks on WASM; shared package definitions remain the wire-contract authority.
- `ManageSubCustomerAccountView` creates with the injected parent's UUID through `API.custSubAcctV1.create`, checking outer/create response statuses and the returned parent ID. Editing validates the source parent, uses `update` with the source UUID/status, then `load(.id)` to return the server's record after verifying its ID and parent. Both paths retain `longitud` and validate returned full address/coordinates when required.
- `API.custSubAcctV1` uses the shared `CustSubAcctComponents` contracts under `custSubAcct/v1`. Create/load/update use authenticated POST; account-scoped search uses authenticated GET and decodes a raw `[CustSubAcct]`, retaining the searched term in its callback and returning nil on transport/decoding failure. Create/update expose labeled parameters and construct the shared request objects internally, preserving the coordinate wire key `longitud`; load accepts `HybridIdentifier`.
- Asset architecture uses `listStoreArchitecture(relationId:)` and department creation requires a nonoptional `relationId`. Location links use `CustCommercialAssetsLocationLinkedType`; asset-item links retain `CustCommercialAssetsLinkedType`. Asset `custAcct` fields remain customer-account identifiers, not store or warehouse identifiers.
- Asset-item creation uses TCFireSignal's shared `InitiateAssetItemViewType`, `CreateAssetItemObject`, and `CreateAssetItemFile` contracts. Single creation submits one object; batch creation collects the requested objects before one request, and `CreateAssetItemResponse.items` returns every created asset item.
- Registration-store selection reaches asset creation through the existing `CreateAssetItemRequest.type`, with the selected `CustStore` embedded in the original enum case. Customer/subcustomer ownership records stay intact; the shared latitude/longitude derive from that physical store. Single and batch callers forward this resolved context without an extra store wire field or wrapper change.
- Before presenting either asset-item creation form, `AssetView` requests `getAssetsSection(type:)` with that same resolved registration type. Its `sections` and `subSections` arrays replace the view's previous options, so the form uses the selected store's hierarchy. A failed request or missing response data prevents opening a form with stale choices.
- Asset-item listing uses the shared `ListAssetItemsType` location scope, optional `departmentId`/`categorieId` filters, and `ListSubAccountItemsStatus` filter in `ListAssetItemsRequest`, posting to `listAssetItems` and decoding `ListAssetItemsResponse.items`. Store/warehouse scopes take `storeId` and an optional owning `account`; the backend treats a nil account as unowned inventory. Account scope takes `account`, optional `storeId`, and optional `loadSubAccounts` (nil: all, true: linked, false: unlinked). Subaccount scope selects by `owningSubAccount` rather than current custody location.
- Trip asset search requires linked store/warehouse/subaccount endpoints. Store/warehouse requests use `.store(storeId:account:)` or `.warehose(storeId:account:)` (shared wire spelling) with the trip's customer `account.id` and active status. Subaccount pickups request account inventory with unavailable status, then match the exact physical `currentLocation`/`currentLocationId`; owning subaccount is not a substitute for custody after a trip. The picker and selection callback retain those origin/status checks. Inventory loads before picker presentation; the selected item's parent `getAsset` metadata loads before fiscal editing. Commercial-asset trip merchandise links to `CustCommercialAssetsItem.id`, not its parent `commercialAssetId`, and keeps that identity through the existing trip submission contract.
- Asset-item detail uses TCFireSignal's shared `GetAssetItemRequest(itemId: HybridIdentifier)`/`GetAssetItemResponse` on the exact `getAssetItem` POST route. The detail view accepts UUID and folio identifiers; inventory opens `.id(item.id)` and Work asset folio search opens `.folio(term)`. The returned concrete item's UUID is retained for Kardex and warranty-card operations, which stop when no UUID has loaded. Its response includes the parent asset, and resolved location/inventory payloads use `GetAssetItemLocationType`, identifying the current store, warehouse, account, subaccount, or user; detail records retain optional department, category, section, and subsection classification.
- Asset creation and update preserve the shared commercial-asset fiscal and physical fields: `fiscCode`, `fiscUnit`, `width`, `height`, `length`, and `weight`.
- Asset, asset-item, location, sublocation, category, and department update responses return the inserted `CustGeneralNotes` entry when a change produced an audit note; successful no-op updates may return no note.
- Commercial trip creation submits the complete fiscal location fields for each stop, together with `LocationType` and an optional linked ID; the server persists those submitted snapshots.
- Fiscal merchandise items distinguish their own UUID from `merchandiseType` and optional linked `merchandiseId`. `AddCartaPorteMerchendise` preserves those source fields on save; new manual entries use `.merchandise` with no linked ID. `CreateTripView` forwards type and linked ID to the shared `TripMerchandise` request, retaining its legacy item-ID fallback; deleting a saved merchandise base matches only `.merchandise` sources by linked ID (or item ID for legacy unlinked items).
- `CreateTripView` receives, edits, and submits `CustCommercialTripsComponents.TripLocation` snapshots directly. Its legacy UI adapters retain a nullable `locationId`; an item UUID generated for display/editing is never promoted to a submitted source ID.
- Order payment forms submit the explicitly selected `downpayment` boolean through TCFireSignal. Service/rental creation carries it in `PaymentObject`; later order payments carry it in `AddPaymentRequest`. The form defaults false even with no outstanding balance. Reports partition the shared payment list by that flag into Pagos generales and Anticipos, show each subtotal and their combined total, and export both groups/subtotals in the payment CSV. Existing payment/adjustment arithmetic is preserved; older payloads without the flag decode false.
- Order processing reports consume `ReportsResponseGeneral.delivered` from TCFireSignal. Each entry has an equipment delivery timestamp, order summary, equipment identifiers, and a current pending-equipment flag; the view and CSV export keep it separate from created orders, closed orders, and payments.
- Order charge and payment deletion use the `restrictDeleteCharges` and `restrictDeletePayments` thresholds. Users below the applicable threshold request approval through `CustTaskAuthRequestWaitView`; an approved WebSocket result reloads the order, while the direct removal response is applied only when its `auth` value is true.
- Price override views pass TCFireSignal's `ChangePriceAuthorizationContext` to `CustTaskAuthRequestWaitView`: order and order-budget charges use `restrictOrderCharges`, sale/account/fiscal charges and non-merma transfers use `restrictSaleCharges`, and inventory merma uses `restrictMermProduct`. The server uses the same context when selecting task approvers; requests without the context retain the former level-five gate. A `changePrice` response with `actionType: notify` completes the wait immediately when server settings already permit the requester.
- `Package.swift` resolves TCFireSignal from its remote `main` branch, so PWASkyline needs a revision containing this shared price-authorization contract before it can build with these callers.
- Trip store snapshots use the store-linked fiscal profile when available, otherwise the main profile (`FIAccountsType.account`). A missing preferred/main cached profile triggers the existing general `getProfile` request; a failed/unresolved lookup can use the cached main profile, and absence of any usable profile reports the requested fiscal-configuration error. This picker does not mutate the global fiscal-profile cache.
- Endpoint files are grouped by domain and often named `Domain+Action.swift`.
- The app depends on multiple Tierra Cero core packages that likely define shared payloads and contracts.
- The three public `sendPost` overloads share one internal XMLHttpRequest transport that preserves response-body callback compatibility while recording transport failures.
- First-party TierraCero and IntarTC `XMLHttpRequest` transports send the current `custCatchChatConnID` in the `WSId` header so backend work can correlate asynchronous WebSocket updates with the originating browser connection.
- API wrapper decoding is routed through `decodeAPIResponse`, except the recursion-protected error-reporting endpoint response.
- `API.v1.reportError` uses the shared `ReportErrorRequest` contract and a reporting-disabled transport policy.

- The existing `saveCommunicationProfile` wrapper sends all 28 named `notifyOn…: [String]` fields directly. The server saves each corresponding profile list; every recipient field is required and an empty array clears its list. Source reviewed; build verification remains unrun.

- `notificationsSaveSettings` sends seven required named CustPushNotificationAlertFrequency arguments together with the existing PWA reminder frequency and level. The server persists them per user, and the PWA updates its local AlertManagerConfiguration only after success. Older stored configuration JSON defaults the new group fields to silent. Source-reviewed; builds/runtime verification remain unrun.

- Shared CTAM full/Quick responses include alertFamily, optional alertFrequency, and optional notified. Legacy transport payloads decode to general/nil/nil. The server preserves these fields through list/detail/order queries and WebSocket copies; existing PWA renderers consume the extended shared types without a route or UI change in this metadata stage.

- Equipment payloads carry shared `CustFolioObjectsType` (equipment/assetItem), defaulting legacy JSON to equipment. Equipment status/cache DTO copies retain the existing type. Contract relation keys include type with a human-readable label/value and optional relId as an asset UUID string. Shared equipment creation/list payloads carry relId after type, defaulting missing/null values to nil; all three browser equipment status/cache copies retain it. Existing service-tag fields keep their meaning.
- Asset-item service-order creation uses the existing `custOrder/v1/create` request with one `EquipmentObject(type: .assetItem, relId: item.id)` and the asset owner's account. The request `store` is the current physical store/warehouse UUID, not `owningStore`. The server remains authoritative for current-location operation type, active status, account ownership, and trip/order reservations; the browser preflight only controls button visibility. Reservation and release are recorded with the existing `assetUpdate` Kardex context and the order UUID, preserving compatibility with clients pinned to the shared payload. Finalizing requires every equipment/rental line to be delivered and makes the asset active; canceling requires the same pickup completeness and sends it to tomerm. The server validates saved line IDs and rejects incomplete or undelivered requests before writes, including legacy turnout delivery. Generic terminal status changes and recovery of pickup on a closed asset order are rejected. No new order wire route or local DTO is introduced.

## Rules

### API-001 — Client Contract Ownership

API wrapper files own client-side request construction, response decoding, callbacks, and error propagation for their domain.

### API-002 — Backend Contract Drift Requires Review

Any change to endpoint paths, payload shape, auth headers, fiscal fields, payment fields, or expected response models must be treated as a backend contract change unless verified against backend/shared package definitions.

### API-003 — Fiscal and Payment Focus

Fiscal, CFDI, Carta Porte, payment, credit, and account-balance flows require especially small diffs and focused verification because mistakes can affect legal/accounting behavior.

## Implementation Guidance

- Preserve exact serialized keys and backend naming conventions.
- Add new endpoints in the matching endpoint folder.
- Avoid introducing generic request abstractions in a feature bugfix unless the task is explicitly an API architecture task.
- For new payloads, verify whether the type already exists in a private package before duplicating it locally.
- Error-report delivery succeeds only after a successful HTTP status, decodable response, and backend `.ok` status; delivery failures update the original persisted record and never create a recursive report.
- Diagnostics use `TCFundamentals.ErrorReportingPriorty` directly (`zero`, `low`, `med`, and `high`) for persistence, queue ordering, and backend delivery.

## Vendor Favorite Integration

Vendor create sends favorite (default false); save may omit it to preserve a stored favorite. `setFavoriteVendor` posts shared `SetFavoriteVendorRequest(vendorId:favorite:)` and decodes `APIResponse`. `getVendors(type:)` sends the shared list request, defaulting all. SearchVendorView and product-vendor matches render a separate star action that preserves selection/add behavior; state changes after `.ok` only. Search results and edits retain the returned favorite field. Source reviewed; builds, tests and browser verification have not run for this change. Deploy the updated shared packages/server and apply the vendor favorite column SQL before enabling the client.

## Trip Asset Service Eligibility

The CreateTripView inventory picker excludes commercial asset items with a non-null `serviceTrip` or `serviceOrder`, and its final selection callback rechecks both fields to reject stale search results. SkylineServer repeats eligibility validation under the asset row lock before trip creation.

## Order File Kardex Reference

Order-file lists use the shared TCFundamentals `CustOrderLoadFolioFiles` payload, which includes optional `kardexId` after `item`. PWASkyline has no duplicate local file model; old responses decode with a nil value. `Package.swift` resolves TCFundamentals from remote `main`, so this field becomes available after the shared change reaches that branch and PWASkyline refreshes the dependency.

## Order Media Item Association

OrderView links uploaded order files to a folio object only when exactly one equipment or asset item is present. It sends that `CustFolioObjects.id` as `itemId` to the existing upload manager. Order-message camera requests carry the same optional ID through `RequestMobileCamaraRequst`; callers outside an order keep the nil default. TCFireSignal and TCFundamentals own the shared request and APNS payload fields, so their revisions must be available to PWASkyline before refreshing its remote-main dependencies.
